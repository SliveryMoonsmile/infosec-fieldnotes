A packet capture is an observation from one location. Start by identifying the layer and the capture point before deciding what the traffic means.

Read from the outside inward

For an ordinary Ethernet/IP/TCP capture, distinguish link addresses, IP addresses, transport ports, and application data. TCP establishes connection state through its handshake; a SYN is the start of that exchange, not proof that an application request succeeded. A port number is a useful clue, not a guarantee of application identity. [4]

Answer the ARP question locally

The notebook asks where ARP information lives. On Linux, ip neigh show displays the kernel’s neighbor entries. For IPv4 these are the ARP table: bindings between protocol addresses and link-layer addresses on a shared link. Record the interface and entry state with the address. [3]

# Read-only inspection on a Linux lab machine.
ip neigh show

# Read a capture you are authorized to inspect.
tcpdump -nn -r lab.pcap -c 20

The second command does not capture live traffic. It reads at most twenty packets from an existing file; -nn avoids address and port-name resolution. Keep packet captures out of a public repository unless their contents are suitable for release. [2]

Capture filters and display filters differ

Wireshark’s capture filter decides what is collected. Its display filter selects from packets already collected. A display filter cannot recover packets excluded at capture time. Record both filters and the observation point when writing up a result. [1]

DNSSEC and VPNs protect specific boundaries

DNSSEC provides origin authentication and integrity for signed DNS data when validation succeeds. It does not encrypt DNS queries or establish that a destination is harmless. [5]

A VPN is more than changing a source IP. An implementation such as WireGuard authenticates peers and encrypts tunneled traffic; routing determines which traffic enters the tunnel. Protection has endpoints, so identify them before claiming that traffic is protected. [6]
