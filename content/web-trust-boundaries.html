SQL injection, XSS, and CSRF cross different boundaries. Treating all three as a problem solved by “sanitizing the input” hides the defense that each actually needs.

SQL injection: keep data out of syntax

SQL injection occurs when untrusted data changes the structure of a database query. Bind values through the database API rather than assembling them into query text. Table names and sort directions need fixed application choices or an allowlist; value placeholders do not substitute for SQL structure. Limit the database account’s privileges too. [1]

# Python sqlite3: input is a bound value.
row = connection.execute(
    "SELECT title FROM notes WHERE title = ?",
    (requested_title,),
).fetchone()

The downloadable lab creates an in-memory database and looks up a title containing a quote. It verifies that the input remains data and that the table still exists. Python’s sqlite3 API documents these placeholders. [4]

XSS: control the rendering context

Cross-site scripting allows untrusted content to become active content in a page. Use the framework’s safe rendering defaults, context-appropriate output encoding, and maintained sanitization when rich HTML is required. For plain text in the DOM, prefer a text sink. Content Security Policy is another layer; it does not replace safe rendering. [2]

const result = document.querySelector("#result");
result.textContent = userProvidedText;

That example is for displaying text. A value used as a URL, a style, or a script needs a different policy. Naming the destination is part of the review.

CSRF: require intended actions

Cross-site request forgery abuses the browser’s authenticated requests to trigger an unwanted action. Use the framework’s CSRF protection for state-changing requests. Depending on the application, controls include validated tokens, origin checks, and appropriate SameSite cookies. XSS can undermine CSRF protections, so the two reviews remain connected. [3]

Practice: review one form

Choose a form in an application you own. Trace its value to storage and back to display. Then review how the server authorizes the action and validates CSRF protection. Document one positive case and one rejection case for each control. This static publication has no database or authenticated mutations; the examples teach the model for applications that do.
