NOTE 04 / Identity

Identity is the beginning of access.

2 MIN READEDITED 30 OCT 2026

An authenticated user can still be unauthorized. A successful login tells you about identity; access to a particular record requires another decision.

Make permissions explicit

Define a principal, an action, a resource, and any relevant context. A role can group permissions, but owning a role does not automatically justify access to every object. OWASP recommends least privilege, denying access by default, and validating permissions on every request. Test the server’s decision rather than relying on whether a button is visible. [1]

This is a fictional policy matrix. An administrator’s ability to manage identity should be considered separately from access to document contents.

Kerberos: tickets establish identity

Kerberos V5 uses a trusted Key Distribution Center, tickets, and authenticators. A client can obtain a ticket-granting ticket and use it to request a service ticket. The service ticket and authenticator support authentication to that service. Applications still need authorization policy. Base Kerberos relies principally on symmetric cryptography; public-key pre-authentication is an extension, not a requirement for every session. [2]

This corrects the original shorthand that described Kerberos session establishment as necessarily public-key based. Keep authentication protocols separate from directory protocols and from policy models when studying identity.

Test the denied case

  1. Use two test users and two records in an application you control.
  2. Verify that each user can read the record allowed by the policy.
  3. Change the resource identifier and verify the other record is denied.
  4. Repeat after a role change and after the session expires.
  5. Record the expected decision, observed decision, and server-side policy location.

The downloadable CSV gives a small starting matrix. Fill it in before writing the checks. A useful review explains why access is allowed as clearly as why it is denied.
